# M4 S3 调查：哪些舞台可以改用 STD 绘制器（2026-11-01）

依据：`anm/vm.go`（`case 67`、`case 84`、`case 88`、`Start`、`Reset`）、`std/vm.go`（`case 14`）、`anm/anmdraw/anmdraw.go`（`Draw`），以及 `scene/stage/stage.go` 的 `loadSTD`。调查程序是一次性的 `.tmp/scratch/s3survey/main.go`（不在仓库包内，`.tmp` 已被 `.gitignore` 忽略），输出保存在 `.tmp/scratch/s3survey/out.txt`。

---

## 0. 结论

| 舞台 | quad 脚本的模式 | slot 脚本的模式 | 结论 |
|---|---|---|---|
| stage01 | 6, 8（quad 脚本 3、5 为 6） | 无 | 可转换（模式 6 移植后） |
| stage02 | 8 | 无 | 可转换 |
| stage03 | 8 | 无 | 可转换 |
| stage04 | 8 | 0（slot 0 ← 脚本 4） | 可转换 |
| stage05 | 6, 8（quad 脚本 3、5 为 6） | 8（slot 0 ← 脚本 4） | 可转换（模式 6 移植后） |
| stage06 | 0, 8（quad 脚本 0 为 0） | 0（slot 0 ← 脚本 0，slot 1 ← 脚本 10） | 可转换 |
| stage07 | 8 | 8（slot 0 ← 脚本 0；slot 1 ← 脚本 10 的 op 14 在死代码中，见 §3） | 可转换 |

调查时可转换的舞台为 **2、3、4、6、7**。stage01 与 stage05 的 quad 脚本使用渲染模式 6（`anmdraw.Draw` 中的 A1b 模式，当时尚未移植），在 `Draw` 里会 panic，因此这两个舞台曾保留旧背景。

**更新（2026-11-01）**：模式 4、6 已移植（`anm/anmdraw/mode46.go`，FUN_00443b60、FUN_00443f80、FUN_00443fb0），`stdConvertible` 现在包含全部 7 个舞台。`scene/stage/std_smoke_test.go` 的 `TestSTDSmoke` 把每个舞台的 STD 跑 9000 帧，每帧都经过 Node7 和 Node0A 绘制：没有 panic，stage01 与 stage05 的模式 6 quad 确实发出 DrawTL。`TH10_LEGACY_BG=1` 仍可切回旧背景做目视对比。

## 1. 方法

1. **STD 的 quad 脚本**：遍历每个 `Entry.Quads[j]`，取 `ScriptIndex`（即 `Enable` 启动的脚本），与 Type 无关。
2. **STD 的 slot 脚本**：对 STD 脚本做一次线性遍历，步长取每条指令 +6 处的 `int16` size（与 `std/vm.go` 的 `run` 相同）。指令头为 `{u32 time, u16 op, u16 size}`，参数从 +8 开始。对 op 14，`slot = i32(+8)`，`script = i32(+12)`；`script < 0` 只清可见位，不启动脚本，本次调查中没有这种情况。每个 STD 脚本都以 20 字节的 `0xff` 哨兵结束（op `0xffff`、time −1、size −1），遍历在哨兵处停止；遍历终点为 `len − 20`，所有真实指令都已覆盖。
3. **ANM 脚本的模式**：对每个启动的 ANM 脚本，静态扫描其全部指令（不执行）。`case 67` 把 `Flags` 的模式位（bit 22–25）设为 `Arg(0) & 0xf`，因此有效模式为 `Arg(0) & 0xf`。表中同时给出原始参数。
4. **其它写模式位的指令**：`case 84` 把模式置为 9（`Flags = Flags&0xfe7fffff | 0x2400000`）。调查把它计为模式 9；在相关脚本中没有出现。`case 88` 会生成子脚本，子脚本单独绘制，调查按字面 id 递归跟进；在相关脚本中没有出现，也没有非字面的 id。
5. **默认模式 0**：`Reset`（`Flags = 7`）后模式为 0。若第一个模式设置指令（op 67 或 84）在第一次绘制前不可能已经执行，则计入模式 0。判断条件：该指令之前有任一指令的 time > 0、或有任一控制流指令（ANM op 1、2、4、5、28–39），或该指令自身的 time > 0。本次调查的所有脚本，第一个模式设置指令的 time 都为 0，且其前没有 time > 0 的指令或控制流指令，因此 `default0` 均为 false。
6. **缺失的脚本**：`anm.VM.Start` 对缺失的脚本只把 VM 清零（`Flags = 0`），`Draw` 因 `Flags&3 != 3` 而直接返回，所以缺失脚本不绘制，对结论中立。
7. **结论判定**：一个舞台可转换，当且仅当其 quad 脚本和 slot 脚本的全部模式都属于 {0, 1, 2, 3, 8}，且没有非字面的 op 88 id。

## 2. 各舞台的脚本明细

每个脚本的第一个模式设置指令（op 67）的 time 都为 0，`default0` 均为 false。

| 舞台 | 组 | 脚本 | op 67 参数（原始值） |
|---|---|---|---|
| stage01 | quad | 0, 1, 2, 4, 6 | 8 |
| stage01 | quad | 3, 5 | 6 |
| stage02 | quad | 0, 1, 2 | 8 |
| stage03 | quad | 0–8 | 8 |
| stage04 | quad | 0, 1, 2, 3 | 8 |
| stage04 | slot | 4 | 0 |
| stage05 | quad | 0, 1, 2, 4, 6 | 8 |
| stage05 | quad | 3, 5 | 6 |
| stage05 | slot | 4 | 8 |
| stage06 | quad | 0 | 0 |
| stage06 | quad | 1–9, 11, 12, 13 | 8 |
| stage06 | slot | 0, 10 | 0 |
| stage07 | quad | 0–9 | 8 |
| stage07 | slot | 0 | 8 |
| stage07 | slot | 10 | 缺失（不绘制） |

各舞台的 quad 脚本数（按脚本 id 去重）：stage01 为 7 个，stage02 为 3 个，stage03 为 9 个，stage04 为 4 个，stage05 为 7 个，stage06 为 13 个，stage07 为 10 个。

stage06 的模式 0 quad 脚本（脚本 0）只属于 entry 1，而 entry 1 没有任何 face，所以 STD 的 pass 不会绘制它（它仍由 `Enable` 启动并运行）。convertible 判定只看模式，这一点不改变结论。

## 2.1 验证

用一次性的 `.tmp/scratch/s4check`（不在仓库内）对可转换的舞台 2、3、4、6、7 各跑 600 帧的 `Node7` 与 `Node0A`，纹理用同尺寸的替身、sprite 矩形取真实值（本机没有 GPU）。五个舞台都没有 panic。`fogenable` 的调用数在五个舞台上都是 3001，即每帧的固定切换（BeginFrame 一次、Node7 一次、Node0A 三次），没有 pass 内的雾切换，这与上一段的观察一致。

## 3. 不确定与假设

- **静态扫描不执行**：每个脚本的模式集合是其全部 op 67 参数的并集，包含运行时可能不会到达的指令。这使结论偏保守：不会漏掉模式，但可能把一个实际不用的模式算进来。本次调查中，所有不可转换的理由都是实际存在的模式 6。
- **跳转与中断**：静态扫描忽略跳转，也不建模游戏代码触发的标签中断。默认模式 0 的判断已对控制流指令保守处理。
- **stage07 的 slot 1 ← 脚本 10（stage07.anm 中不存在）是死代码**：这条 op 14 在 STD 脚本 pc 0x420（t 8924），位于 pc 0x260 的 op 1（t 5556，跳回 0x230、时间 5300）之后，因此永远执行不到。原作的 STD pc（+0x4c）只有三个写入者：
  - `FUN_00403c80` 的 case 1，即无条件跳转，目标是 `+0x1c`（脚本起点，由 `FUN_00403850` 写入）加上偏移；
  - `FUN_00403c80` 每条指令末尾的顺序前进；
  - `FUN_00404450` 把 pc 复位到脚本起点。

  依据有两条：全部引用主 STD 指针 `DAT_004776e8` 的函数中没有改 pc 的（`.tmp/ecl_dump/stdjmp/`）；同时写 `[reg+0x4c]`、`[reg+0x3c]`、`[reg+0x38]` 的其它函数（`FUN_00415b00` MSG 构造、`FUN_00418d40` calc 链初始化、`FUN_004065c0` 子弹）都不作用于 STD（`.tmp/ecl_dump/stdjmp2/_writes.txt`）。该扫描只覆盖 `[reg+disp]` 形式的存储，不覆盖经 `lea` 算出地址后的间接存储。

  同理，stage03 在 0x118 之后、stage05 在 0xc4 之后、stage07 在 0x260 之后的指令，原作也执行不到（stage05 与 stage07 的第二个 op 1 都跳回第一个循环）。我们的 op 1 模型与原作一致，静态扫描把这些死代码中的模式也算了进去，结论因此只会偏保守。stage06 的 slot 1 ← 脚本 10 在 pc 0x1b0，位于唯一的 op 1（0x264）之前，可以执行到。
- **只统计 op 67、84、88**：调查依据 `anm/vm.go` 中写 `Flags` 模式位的全部位置（`case 67`、`case 84`），本次未发现其它写模式位的途径。
